Live testing found **no matching request at all** for a real search on perplexity.ai -- no REST/SSE call, no GraphQL HTTP call, no XHR beyond an unrelated analytics beacon. The page ships chunks named `threadRelayEnvironment`, `threadLiveUpdates`, `client` (Relay, Facebook's GraphQL client), strongly suggesting Perplexity migrated its thread/query delivery to a Relay-based mechanism, most likely a WebSocket subscription given the complete absence of any matching HTTP traffic. Re-confirmed in a second live pass the same day (same prompt, same result: 0 console errors, 0 captures, no matching network activity at all) -- this ruled out it being a one-off fluke. Per the user's explicit decision, rather than guessing blind at a WebSocket rewrite with no real traffic capture to verify against, Perplexity support was removed from the active extension: `src/platforms/perplexity.ts`/`.ts.test` moved to `archive/perplexity-unsupported/` (not deleted -- the last working implementation, kept for reference if someone captures real traffic later), deregistered from `src/interceptor.ts`'s `PLATFORMS` array, dropped from `public/manifest.json`'s `content_scripts.matches` (both blocks), and its `--clr-perplexity*` tokens/CSS removed. - [x] **Gemini extraction fixed -- the real cause wasn't schema drift.** Investigated 2026-10-08 after the live pass flagged it. The actual bug was architectural, in `interceptor.ts`, not Gemini-specific: the hook-cycle-escape branch (taken whenever another script on the page also wraps `window.fetch` -- gemini.google.com does this for essentially every request) returned the worker-forwarded fetch directly, completely skipping platform detection and `extract()`. Gemini's batchexecute calls never once reached the code path that would have processed them. Fixed by sharing one `attachExtraction` helper across both the direct and escape paths (see git log). Confirmed live afterward: a real query ("1 new query captured") showed up for the first time. That same test also caught a second, real bug: the generic `"text"` key in the fallback matcher (inherited from v1.3) was false-positiving on ordinary response prose (`{text: "I've been curious about..."}` from the assistant's own answer, captured as if it were a search query) -- removed, and a `webSearchQueries`-style array-of-strings shape was added based on Gemini's public grounding API, since the consumer product's internal schema plausibly mirrors it. Both fixes have regression tests. Still worth validating against more live queries to see what else turns up, but the platform is no longer silently non-functional.

- [x] **Fixed Gemini's real capture endpoint never being intercepted -- the actual root cause of its unreliable capture.** User-reported (2026-10-08) after the apostrophe-fix verification above: a live Gemini search ("James Webb telescope" / "glaciers") visibly showed inline source citations in Gemini's own UI, but the overlay captured nothing ("net 9 seen/0 hit"). Investigated via the live network tab: Gemini's real message-generation RPC is `.../assistant.lamda.BardFrontendService/StreamGenerate`, a completely different URL shape from the `batchexecute` endpoint `GeminiContext.shouldIntercept` was checking. Its lowercase `/generate`/`/stream` substring checks never matched "StreamGenerate" (PascalCase, dot-joined to the preceding segment -- confirmed analytically in a throwaway Node script against the real captured URL before touching any code). This means **every previous "working" Gemini capture, including the one that confirmed the earlier re-entrant-extraction fix, came from incidental `batchexecute` side-calls, never the real response** -- explaining the inconsistent hit rate across different prompts. Fixed by matching on `BardFrontendService`. First attempt at the fix used `/BardFrontendService/` (leading slash) and the new test caught it immediately red -- the real path has `assistant.lamda.BardFrontendService` dot-joined, not slash-joined, so the leading-slash check never matched either; corrected to a bare `BardFrontendService` substring check. Also closed a real test-coverage gap: `shouldIntercept` had zero tests before this anywhere in `gemini.test.ts`, which is exactly the kind of thing that lets a casing bug like this ship silently -- added a dedicated suite (4 tests, including the exact live URL).
- [x] **Fixed conversation-switching leaving the overlay stuck on stale data.** User-reported (2026-10-08): "if i skip between earlier convo 1 it just becomes buggy, like convo 1, 2, 3, and then back to convo 2, 1, it just doesn't change anymore." Root cause confirmed by reading `src/content.tsx`: `const conversationKey = getConversationKey(window)` was computed exactly once at content-script load. ChatGPT/Claude/Gemini are all client-side-routed SPAs -- switching conversations in the sidebar changes the URL via `history.pushState`/router navigation, never a full page load, so the content script (which only re-injects on a real navigation) never re-runs and never recomputes the key; every subsequent save/restore kept targeting whichever conversation was active when the tab first opened. Checked `archive/legacy-v1.3/src/conversation.ts` and confirmed the identical pattern existed there too -- a real, long-standing bug, not something the v2.0 rebuild introduced. Fixed in `src/content.tsx`: `conversationKey` is now a mutable `let`, polled against `getConversationKey(window)` every 1s (polling chosen over monkey-patching `history.pushState`/`replaceState` to avoid interop risk with each site's own router); on a detected change, the outgoing conversation's captures are flushed immediately (not left to the 800ms debounced save timer), the in-memory list is cleared, and the new conversation's own persisted history is restored via a `restoreConversation()` helper extracted from `init()` so both paths behave identically. Not unit-tested -- consistent with this file's existing convention as untested entry-glue (no `content.test.tsx` exists, and none of its other effects -- badge updates, debounced save, backfill retry -- are unit tested either); verified via live conversation-switching in the browser instead.

- [x] **Cross-platform re-verification sweep + a second real Gemini bug found and fixed (2026-10-08).** Ran the same search-triggering prompt live against ChatGPT, Gemini, and Perplexity (Claude already covered above) to confirm no regressions. ChatGPT: 5 queries captured, full source lists (up to 22 retrieved per query), zero console errors. Gemini: captured a query, but it was a **false positive** -- `"ve been curious about"`, a truncated fragment of the assistant's own answer, not a real search. Root cause: `runRegexFallback`'s last-resort "quoted term" matcher (`src/platforms/gemini.ts`) treated `'` as a quote delimiter alongside `"`, so the apostrophe in an ordinary contraction like "I've" was misread as an opening quote -- everything up to the next apostrophe/quote got captured as a fake query. This is JSON-based text, where `'` never opens/closes a string; fixed by restricting the delimiter to `"` only. Regression test added reproducing the exact live shape, confirmed red-before-green (`git stash` the fix, test fails with the literal captured string; restore, it passes). Re-verified live post-fix with two separate fresh Gemini conversations: the stats line showed "net 9 seen/0 hit" both times -- zero *new* false positives in either fresh session (the stale "ve been curious about" entry still visible in the panel was a persisted record from before the extension reload, not a live recapture). This is what prompted adding the "Clear all captures" button above, so the stale entry (and any future one) can actually be removed from the UI instead of needing a manual `chrome.storage.local` edit. Perplexity: confirmed the dead-endpoint finding independently (0 console errors, 0 captures, no matching network activity for the same prompt) -- this is what triggered the removal decision above, rather than attempting a second blind fix.

## Explicitly out of scope for v2.0

These came up during the rebuild's design discussion and were deliberately deferred, not forgotten:

- A persistent side panel instead of the floating overlay.
- Cross-conversation search history / search across all captured conversations.
- Side-by-side source comparison across platforms.

If any of these become a priority, they're new features on top of a now-clean architecture, not another rebuild.
